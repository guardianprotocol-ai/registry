# Design decisions

The choices that shape the project, why we made them, and how each stays compatible with where the project is going: a neutral foundation, many implementations, and a shared network. New decisions are added at the end; old ones are never rewritten, only superseded.

| # | Decision | Why | Forward compatibility |
| --- | --- | --- | --- |
| 1 | Apache 2.0 for all code and registry data | The standard license across Linux Foundation projects, with an explicit patent grant | Nothing to relicense on foundation entry |
| 2 | Developer Certificate of Origin, no contributor license agreement | Lowest barrier to contribute; the Linux kernel's model | Foundations accept it as is |
| 3 | Neutral home: the `guardianprotocol-ai` GitHub org | The project must not belong to any company | Org, name and domains transfer to the foundation; company code lives elsewhere |
| 4 | Stable IDs (`GP-0001`), never reused | Sensors, reports and advisories cite them for years | IDs survive schema changes, renames and new implementations |
| 5 | The schema only grows within a major version | Old patterns and old sensors keep working | `schema_version` in every file; breaking changes need a new major version and a migration |
| 6 | Rules are data, never code | A rule can't run anything on a host, and anyone can build a sensor that enforces them | The Python sensor is a reference implementation, not the standard |
| 7 | One shared rule engine for the MCP sensor and client hooks | Same detection wherever an agent acts | New surfaces (gateways, egress proxies) plug into the same engine |
| 8 | MITRE ATLAS and OWASP are mappings, not dependencies | Frameworks update on their own schedules | The coverage map records the ATLAS release it was built from |
| 9 | Open standards for sharing and updates: STIX 2.1, TAXII 2.1, TUF, Sigstore | Existing security tools already speak them | No proprietary formats to migrate away from |
| 10 | Harmless tests: canary tokens and reserved `.test` domains (RFC 2606) | Anyone can run the registry safely | Safe to run in CI, in the scan and in the network |
| 11 | No third-party dependencies in the core for now | Smallest supply-chain surface for a security project | Any dependency added later is pinned and listed |
| 12 | Security Baseline Level 1 from day one | It's what foundation reviewers check | See the checklist below |
| 13 | A result carries one entry per run, not just the totals (`schema_version` 0.2) | `successes: 20` is a number someone typed, and a judge bug looks identical to a real finding. GP-0003 read "sunny" out of the agent's prose and was wrong on half of realistic answers; nobody could tell, because the answers were discarded. A reader must be able to recount the rate | Additive, so 0.1 files stay valid and a re-measurement is a second data point rather than a correction. Built rather than proposed because no contributor had recorded a result yet, which is the only moment this is free |
| 14 | A run log is published, so it is checked for secrets and written as escapes | The log holds verbatim agent output, which on a contributor's machine could be anything. `validate-results` refuses a log carrying a credential, and files are written with JSON escapes so no live invisible character ships. Canary tokens are exempt: they are harmless by construction and a canary in a log is the test working | The check reuses the sensor's own secret patterns, so one list serves detection and publication |
| 15 | Each pattern publishes what its own judge counts | "Attack success rate" over every cell overstated GP-0003, which counts whether a tool whose definition changed was used at all, not whether the agent was exploited. Three of four judges score a real side effect; one reads an answer | The criterion is generated from the judge's own docstring, so the matrix cannot drift from the code, and a new scenario publishes its definition automatically |
| 16 | The lab server logs every tool call | The only ground truth about a run was the side effects two tools happen to write, which left "the agent refused" and "the agent never attempted the task" indistinguishable, and left GP-0003 judged by matching the words "sunny" and "blocked" in the agent's prose. On ten realistic answers that judge was wrong on five, in both directions | One file, `calls.jsonl`, written by the test server only. No change to the protocol, the patterns or the sensor. A real harness is still measured from outside |
| 17 | A run that never opened the attack vector is counted, not folded in | An agent that declines the task did not resist an attack, it did not take part in one. GP-0008 scored 0 of 20 while the agent delegated at all in only 9 of 20 runs. Counting those as defences would let a fall in capability read as a rise in security, and quietly excluding them is how a denominator gets chosen after seeing the result. So `attempted` is published beside the rate and both denominators appear in the matrix | Additive: a scenario with no precondition records nothing, and `rate` keeps its existing meaning so every earlier file stays valid. The precondition rate is itself a measurement, and it is what surfaced that the sensor may suppress legitimate handoffs |
| 18 | A rate needs 20 trials that opened the vector, and the floor is reported rather than enforced | Twenty is where a clean result becomes publishable: 0 of 20 supports "under 16%", 0 of 8 only "under 37%". The floor is on valid trials because GP-0008 passed every check at 20 runs while carrying 8. It is a note, not a refusal, because refusing throws away the measurement and the attempt rate together, and the attempt rate is a property of the agent worth measuring | `--until-attempted` targets trials instead of runs with a hard cap, so reaching the floor is one flag and always terminates. Cells below the floor stay in the matrix, marked, so absence of evidence is visible rather than silently dropped |
| 19 | A scenario may count more than one thing about the same runs | One success rate cannot say that an agent noticed an attack, refused what it asked for, and was compromised anyway. For GP-0003 that combination is the finding: 20 of 20 used the changed tool, 19 of 20 named the injection, 0 of 20 obeyed it. The model's judgement worked and it did not matter | Counts sit beside the rate and never inside it, so the verdict stays one number computed one way. A dimension that raises is recorded false rather than failing the run. Every dimension needs a test proving it can fire in both directions, because a detector that is always false is indistinguishable from a broken one, and the file states which dimensions are read from the server's record and which from prose |
| 20 | The exchange is the headline, not agent vulnerability | A literature search in October 2026 found the catalogue and the outside-in scan already built: MCPSecBench, ETDI, OWASP MCP03:2025 and a public transparency log over 13,870 MCP servers. What nothing covers is the inside of a deployment. A national AI information sharing centre is in development under DHS, whose builders have said they want to avoid duplicating existing private capability, and what no one has is the reporting format such a centre would consume. Meanwhile real agent intrusions in 2026 were found after the fact, because incident tracking is people reading disclosures and adding rows by hand. Separately GP-0003 measured 0 of 20 against a hardened harness, so a claim resting on agents being broken rests on a vendor staying broken, and an absence does not get patched | No redesign: the network and hub v0 were already specified here, so what changes is order. The hub moves ahead of the words-domain work, and the sensor is restated as the reporter rather than only an enforcement point. The scanner keeps its job, because an exchange that cannot validate a submitted pattern is a rumour mill |
| 21 | A sighting says whether it came from real traffic or from a fire drill (`source`, sightings `schema_version` 0.2) | Joining the exchange used to mean waiting to be attacked, so the drill brings the attack: a member runs it against their own machine and gets real detections from their own sensor in about a minute. Those detections are genuine, and they are not incidents. Without a mark they are indistinguishable once aggregated, and a paper reporting exercises as observed incidents would be the same overclaim rows 13 to 19 exist to prevent. The mark is written by the sensor at the moment of detection, because that is the only place that knows for certain | Additive and a fixed vocabulary of `live` and `drill`, never free text, so the allow-list argument still holds at eight fields. A 0.1 file stays valid and a missing source reads as live, which is safe only because a drill marks itself: the sole way to be unmarked is to be a record no drill touched. Refusing older files would make every future field a breaking change to a format other organizations have already written to disk. Aggregation takes `--source` and states which it counted when nothing is passed |
| 22 | The sightings format is a specification, and the sensor is one implementation of it | The format was defined by `hub.py` and described in prose. That makes it a tool with a file format rather than a protocol: anyone writing a second sensor had to read our Python to learn what a sighting is, and a foundation will ask for the thing the implementation conforms to. The patterns already had `schema.yaml`; the format the whole exchange turns on had nothing | `spec/sightings-0.2.md` is normative for meaning, `spec/sightings-0.2.schema.json` for shape, and `spec/tests/test_conformance.py` reads both and compares them against the code, so a change to either side that the other has not sanctioned fails. The spec states the reasoning, not only the constraints, because an implementer who knows why an hour is coarse will not helpfully add minutes. Open questions are listed in it rather than left for someone to discover: no signing, no transport, and whether proof of possession justifies a lower floor |
| 23 | An operator registers their own canaries, stored as salted digests, and a canary earns the right to block | Every other detection is a pattern written in advance, which is what an adaptive attacker reads and routes around, and the only values the sensor knew were our own test tokens. A canary detects by invariant instead: it fires because a specific value moved, whatever moved it, so it keeps working against a technique nobody has catalogued. The Railway disclosure is the case, where customers learned their keys were taken from an announcement rather than from instrumentation | Only a salted digest is stored, because a file listing what the sensor watches for would otherwise be a worse secret store than the one it protects, and an unsalted digest of an API key is the key to anyone holding the vendor's key space. Candidate tokens in outbound arguments are hashed and compared, since hashing the whole body would miss a value inside a larger message. The value is read from a prompt or a pipe, never an argument, and never appears in evidence, a log line or an error. A canary starts in `baseline` and reports without blocking whatever the mode: legitimate processes touch things nobody should touch, and the first thing an operator learns from a badly placed canary must not be that their agent stopped. Kept separate from GP-0002 because the trust differs, not the mechanism: a registered canary could not have been fabricated without access, while a pattern match is a guess about shape, and those justify different thresholds in an exchange. A refusal names no rule, the same text for every one: an attacker holding stolen credentials can send them one at a time and read the answers, so a distinguishable canary refusal tells them which key is the fake and they take the rest. Naming every rule except canaries does not fix it, because the unnamed answer is then the signal. The cost is that a developer reads the evidence log to learn why a legitimate call was blocked, which is a better trade than telling an adversary which of their keys is bait |
| 24 | Participants poll a published agenda, and nobody can invoke anything on their machines | Coordinating many busy participants to act in the same hour does not work, and the natural fix is worse than the problem. A channel that lets an operator invoke actions on participants' machines is a botnet whoever runs it: the most attractive target in the system, and something that would have to be removed before production, so whatever it proved would not be what shipped | An agenda carries a time, never an action, and a document with any other field is refused rather than ignored, because ignoring an unknown key means a later version would obey what an earlier one dropped. The action is fixed in the installed code and is the same local exercise the operator can run by hand. Compromising the publishing point therefore buys an attacker one consented local drill, which is why this is a static file rather than a service. An exercise runs at most once however often it is polled, since an hourly poll would otherwise repeat it forever. Specified in `spec/agenda-1.md`, with the absence of a signature stated there |

## OpenSSF Security Baseline Level 1 checklist

| Control | Requirement | Status |
| --- | --- | --- |
| OSPS-AC-01.01 | Multi-factor authentication for everyone with write access | Done: required for the org, Oct 4 2026 |
| OSPS-AC-02.01 | New collaborators get the lowest permissions by default | Done: the org's base permission is Read |
| OSPS-AC-03.01 | No direct commits to the main branch | Done: branch protection on `main` requires a pull request and the `check`, `signoff`, `status-guard` and `rule-safety` checks |
| OSPS-AC-03.02 | Deleting the main branch needs explicit confirmation | Done: deletions and force pushes are both refused on `main` |
| OSPS-BR-01.01 | CI inputs are validated | Done: `.github/workflows/checks.yml` runs `check.py` on every push and pull request, with a read-only token, actions pinned to commit SHAs and no secrets exposed to forks |
| OSPS-BR-03.01 | Official links use HTTPS | Done |
| OSPS-DO-01.01 | User guide for basic use | Done: `README.md`, `demo/README.md`, `sensor/README.md` |
| OSPS-DO-02.01 | How to report defects | Done: GitHub issues; `SECURITY.md` for vulnerabilities |
| OSPS-GV-02.01 | Public place to discuss changes | Done: GitHub Discussions, plus `docs/proposals/` for designs under decision |
| OSPS-GV-03.01 | Contribution process documented | Done: `CONTRIBUTING.md` |
| OSPS-LE-02.01, 02.02, 03.01, 03.02 | OSI-approved license in a LICENSE file | Done: Apache 2.0 |
